# Repository Instructions

- Derive every plug-in build version from the latest modified source `*.cs` file, using `yy.M.d.Hmm` with no seconds and non-padded month, day, and hour.
- Keep tracked text files on CRLF line endings through `.gitattributes` so builds do not emit Git conversion warnings.
- Route runtime diagnostics through the shared `Log` helper; keep the log beside the loaded DLL, clear it on startup, and record both plug-in and Rhino versions in the startup entry.
- For Rhino script files that define `VERSION`, use `yy.m.d.hmm` with no seconds, non-padded month/day/hour, and two-digit minutes; example: `26.7.8.1830`.
- Immediately after every agent-made project change, create or refresh the pending summary with `build.ps1 -ComposeOnly -Message '<specific behavioral summary of all uncommitted changes>'`; do not defer this until build time. Regenerate the summary from the current net diff against `HEAD`, never as an append-only work log. A manually launched workspace build must reuse that summary and prompt only when none exists.
- Never generate or accept filename/category-only commit summaries such as `panel: update`, `plugin: update`, or `build: align release workflow`; the build must fail when its semantic message is missing or generic.
- Keep commit and pending summaries consolidated and concise: state only the net behavior or build workflow changed between `HEAD` and the worktree, or between a commit and its parent, without implementation details. Omit intermediate changes that were fully reverted before the commit.
- `build.ps1` without options must perform a standalone Release build with no Git requirement, commit, or push. Before checking DLL locks, it must skip compilation successfully when both Release DLLs already match the source-derived version and are not older than the latest C# source. Use `build.ps1 -Publish` or the normal workspace build task for the publishing flow.
- After agent-made project changes, run the standalone no-commit Release build whenever neither tracked Release DLL is locked. If either DLL is locked, build both target frameworks in Debug instead. Agents must leave staging, commits, and pushes to the user.
- Check the actual Release DLL locks only after all investigation, debugging, and edits are finished, immediately before invoking a compiler or build script. Test each DLL with an exclusive read/write open; do not infer lock state from Rhino processes or windows. Never reuse, report, or make a build decision from an earlier lock check; perform a fresh check directly before every compile or build.
- In the publishing flow, skip compilation when both Release DLL versions match the source-derived version and neither DLL is older than the latest C# source; continue the normal commit/push flow with those outputs even if a DLL is locked. If compilation is required and either DLL is locked, skip the build before either target is changed and preserve the pending message. Otherwise, automatically commit and push only when a successful Release build changes the tracked Release DLL. Sign the commit, push `master`, and preserve the pending message if the commit fails.
- Use the `(No Commit)` workspace build task for a Release build that must not commit or push.
- Build versions shown in a README must be updated automatically by a successful Release build. Command versions in README command lists are introduction versions and must not change when commands are updated.
- Commit messages describe plug-in behavior and build changes; do not mention source script filenames.
- Keep paths relocatable. Do not embed machine-specific absolute paths in the plug-in or its runtime files.
- Undo/Redo command behavior should be implemented as hidden features. Do not show Undo or Redo as visible command-line options, and do not list them in visible command option sections.
- Put every command and helper option default in a clearly labeled defaults block at the top of the file's primary source type, before keys, helper types, methods, and mutable runtime state. Monitor and helper types in the same file must reuse that top block. Use named constants or static readonly values for defaults, initialize option state from them, and reuse them in config-loading fallbacks instead of burying default literals in methods. Add a concise inline note to every default declaration describing its accepted units, range, format, enum, or sentinel; for booleans, state the behavior of both `true` and `false`. Also annotate every customizable constant that affects appearance, interaction, output naming or placement, limits, timing, tolerance, or sampling so its purpose and expected value are clear.
